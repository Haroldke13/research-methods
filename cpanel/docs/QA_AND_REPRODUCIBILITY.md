# QA, Reproducibility, and Data-Handling Controls

## Quality safeguard

Every run follows a **declare → validate → analyze → serialize → review** gate. Required columns are validated before inferential code runs; duplicate IDs and missingness are surfaced; outputs preserve the declared study specification; and the program emits JSON, CSV, Markdown, and a diagnostic figure from the same run.

## Reproducibility

- Demonstration data are generated with a fixed seed (`20260918`).
- Demo data contain synthetic identifiers and no real people.
- The analysis specification is versionable JSON.
- Statistical outputs are generated by code rather than copied into the report.
- Tests cover both successful analyses and expected failures.
- `scripts/validate_repo.py` verifies required files plus Python/JSON syntax.

## Provenance

For client work, preserve these alongside the repository or in an approved data-management system:

1. source file name and checksum;
2. extraction/export date;
3. source system or survey wave;
4. codebook/data dictionary version;
5. analysis specification version;
6. transformation log;
7. exclusion log;
8. analyst/reviewer sign-off.

The sample repository does not invent source provenance for external data because none was supplied.

## Runtime upload handling

The Flask application is local-first. Uploaded CSVs are placed in `runtime/<run_id>/`, which is excluded from Git. Each results page includes a deletion action that removes the uploaded dataset, copied specification, and generated output directory for that run.

For production deployment with personal/confidential research data:

- terminate TLS at the reverse proxy;
- require authentication and role-based authorization;
- store uploads outside a public/static path;
- encrypt storage and backups according to organizational policy;
- define a retention period and automated deletion job;
- record access/audit events;
- avoid public PaaS deployment unless the data-processing agreement and data classification permit it.

## Statistical review gate

Before publication or client handoff, a reviewer should confirm:

- the estimand matches the research question;
- the model matches the sampling/design structure;
- primary vs secondary analyses are labeled;
- missing-data handling is justified;
- effect sizes and intervals are reported;
- causal language does not exceed the design;
- multiplicity is addressed when relevant;
- tables/figures trace back to generated artifacts;
- limitations are stated.
